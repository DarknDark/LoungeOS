LoungeOS – Module 1.5: Complete the Production Architecture (No Customer Features Yet)

Excellent work.

The architecture review was honest and confirms we have a strong blueprint, but the production architecture is not yet complete. I agree with the assessment that Module 2 should not begin until the remaining architectural decisions are finalized.

This is the final architecture pass before feature implementation.

Objective

Transform the current architecture from contracts and documentation into a working production foundation, without building customer-facing or staff-facing features yet.

Do not create UI screens beyond what is required for testing architecture.

Do not continue expanding the existing prototype.

Instead, complete the production backbone that every future module will depend on.

1. Finalize the Persistence Strategy

The review identified an unresolved persistence decision.

LoungeOS will use Firebase Firestore as the primary operational database.

Keep PostgreSQL/Drizzle only if it has a clearly documented future purpose (for example reporting, warehousing, or exports). Otherwise remove the unused scaffold.

After this step there must be one authoritative persistence strategy.

5. QR Session Rules

Implement the production rules.

A QR scan must:

validate the table
ensure only one active table session exists
prevent replay
create an anonymous customer session
assign the first customer as the session owner

The owner controls:

ordering
running tab
inviting contributors
closing the bill

Additional contributors receive temporary payment tokens only.

They cannot modify orders.

6. Split Bill Rules

Implement the business rules only.

Do not build UI.

The owner specifies:

"How many additional contributors will help pay?"

Generate secure payment tokens.

Each token:

belongs to one contributor
expires automatically
can only be used once
can only pay toward that table session
