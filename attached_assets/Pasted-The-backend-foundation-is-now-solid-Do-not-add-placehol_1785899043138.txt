The backend foundation is now solid. Do not add placeholder features or fake authentication. From this point onward, focus on making the application behave exactly like a real nightclub.

1. Replace polling with realtime

The waiter dashboard should update automatically.

Whenever any of these happen:

customer places order
customer presses Pay Now
customer presses Close Tab
customer requests waiter
customer requests a song
payment is confirmed
waiter closes table
waiter reopens table

the dashboard should update immediately without refreshing.

If Firebase listeners are available for authenticated staff, use them.

If not, use lightweight polling (3–5 seconds) until realtime is connected.

6. SMS Receipt

Design the system so receipt providers are pluggable.

After payment confirmation:

M-Pesa / Till

Automatically send an SMS receipt to the payer's phone number (retrieved from the payment transaction).

No prompt required.

Cash

Ask:

Would you like your receipt by SMS?

If yes:

Collect phone number.

Send receipt.

Otherwise print if printing is available.

Do not hardcode any SMS provider yet.

Create a ReceiptService interface so Africa's Talking, Twilio, or another provider can be added later without changing business logic.

7. Customer Ownership

Keep the permanent QR philosophy.

The QR identifies only the table.

Never the customer.

Scanning creates a new customer session.

Ownership belongs to the active session, not the QR.

The QR should live on the table for months or years and should not need to be reprinted after every customer.

8. Before Building Anything Else

Do not start Module 4.

Finish and polish the complete table lifecycle first:

This keeps the focus on delivering a polished, reliable experience before adding new features.
